
## Audit & Perbaikan Riwayat Trip (2026-10-07)

### Masalah yang Diidentifikasi

1. **HistoryScreen.tsx** - Tidak melakukan refresh data saat komponen mount atau saat window mendapat focus
2. **HistoryDetailScreen.tsx** - Fallback `?? myTrips[0]` menampilkan trip yang salah saat trip target tidak ditemukan
3. **Data tidak sync** - Perubahan trip dari layar lain (mis. trip baru di-commit) tidak langsung muncul di Riwayat

### File Diperbaiki

#### 1. `mobile/src/pages/mobile/HistoryScreen.tsx`

**Masalah:** Komponen tidak re-render saat data trips berubah dari store atau saat navigasi balik dari layar lain.

**Solusi:**

```typescript
// Tambah state untuk force refresh
const [refreshKey, setRefreshKey] = useState(0)

const refreshTrips = useCallback(() => {
  setRefreshKey(k => k + 1)
}, [])

useEffect(() => {
  // Initial refresh on mount
  refreshTrips()
  
  // Refresh saat window mendapat focus
  const handleFocus = () => refreshTrips()
  window.addEventListener('focus', handleFocus)
  
  // Refresh saat localStorage berubah (cross-tab sync)
  const handleStorage = (e: StorageEvent) => {
    if (e.key === 'trip.trips.v1') refreshTrips()
  }
  window.addEventListener('storage', handleStorage)
  
  return () => {
    window.removeEventListener('focus', handleFocus)
    window.removeEventListener('storage', handleStorage)
  }
}, [refreshTrips])

// Force re-render dengan key pada list
const tripsKey = `${refreshKey}-${trips.length}-${officer.name}`
// ...
<div className="space-y-3" key={tripsKey}>
```

**Perubahan kunci:**
- Mount trigger refresh data dari localStorage
- Focus event trigger refresh
- Storage event trigger refresh (sinkronisasi antar tab)
- Key pada list memaksa React re-render dengan data terbaru

#### 2. `mobile/src/pages/mobile/HistoryDetailScreen.tsx`

**Masalah:** Fallback `?? myTrips[0]` menampilkan trip yang salah jika trip dengan `detailTripId` tidak ditemukan atau bukan milik officer ini.

**Solusi:**


**Perubahan kunci:**
- Tidak ada fallback `?? myTrips[0]` yang menampilkan trip acak

## Audit & Perbaikan Sync Queue Anti-Lock (2026-10-07)

### Masalah Kritis yang Ditemukan

#### mobile-trip/src/services/offline-sync.ts

1. **Queue Lock Bug (KRUSIAL):** `processItem()` menghapus item dari antran TANPA verifikasi HTTP response yang tepat. Jika koneksi timeout atau error sebelum response diterima, item bisa hilang dari antran tapi tidak sampai server.

2. **Tidak ada probeServer():** `processQueue()` hanya cek `navigator.onLine`, tidak probe server.

3. **Tidak ada autentikasi sesi:** Request POST tidak verifikasi token sebelum kirim.

4. **Timeout protection tidak ada:** Request bisa menggantung selamanya.

5. **Retry logic tidak ada:** `retryAll` parameter di fungsi tapi tidak dipakai.

### File Diperbaiki

#### `mobile-trip/src/services/offline-sync.ts` (arsitektur v4)

##### 1. processItem() — Anti-Queue Lock

**MASALAH:** Item dihapus dari antran hanya karena `res.ok` (semua HTTP 2xx), tidak termasuk 200/201 saja.

**PERBAIKAN:** Verifikasi ketat HANYA HTTP 200 ATAU 201.

```typescript
// SEBELUM (BUG):
if (res.ok) {
  await removeSyncItem(syncId)  // Semua 2xx menghapus item!
}

// SESUDAH (FIX — KONFIRMASI SERVER):
const statusOk = response.status === 200 || response.status === 201

if (statusOk) {
  // BARU item boleh dihapus dari antran
  await removeSyncItem(syncId)
}
```

##### 2. processItem() — Timeout Protection

**MASALAH:** Fetch bisa menggantung selamanya tanpa batas waktu.

**PERBAIKAN:** AbortController dengan timeout.

```typescript
let response: Response | null = null
try {
  const controller = new AbortController()
  const timeoutId = setTimeout(() => controller.abort(), ITEM_TIMEOUT_MS)
  
  response = await fetch(url, { signal: controller.signal })
  
  clearTimeout(timeoutId)
} catch (error) {
  // Timeout/error jaringan → item TETAP di antran
  const updated = { ...item, attempts: item.attempts + 1, lastError: errorMsg }
  await dbPut('trips', syncId, updated)
  scheduleRetry(backoffTime)
  return
}
```

##### 3. processQueue() — Probe Server Sebelum Proses

**MASALAH:** Hanya cek `navigator.onLine`, tidak verifikasi server reachable.

**PERBAIKAN:** Probe server dengan `/api/health` sebelum memproses item.

```typescript
async function processQueue(opts = {}) {
  // 1. Probe server TERLEBIH DAHULU
  if (!opts.force) {
    const serverOk = await probeServer(true)
    if (!serverOk) {
      scheduleRetry(POLL_INTERVAL_MS)
      return
    }
    
    // 2. Verifikasi sesi autentikasi
    const sessionOk = await ensureBackendSession()
    if (!sessionOk) {
      scheduleRetry(MAX_BACKOFF_MS)
      return
    }
  }
  
  const items = await dbAll<SyncQueueItem>('trips')
  
  for (const item of items) {
    // Probe di setiap item (jaringan bisa putus di tengah proses)
    if (!opts.force && !(await probeServer(true))) {
      break
    }
    await processItem(item, opts.retryAll)
  }
}
```

##### 4. Backoff & Retry Logic

**PERBAIKAN:** Exponential backoff bertingkat + retry cerdas.

```typescript
function backoffMs(attempts: number) {
  // 15s → 30s → 60s → 120s → ... → cap 10 menit
  return Math.min(BASE_BACKOFF_MS * Math.pow(2, attempts - 1), MAX_BACKOFF_MS)
}

// Retry cepat untuk error jaringan (< 2 detik)
const fastRetry = item.attempts < 3 && isNetworkError(errorMsg)
scheduleRetry(fastRetry ? FAST_RETRY_NETWORK_MS : backoffMs(updated.attempts))
```

### Prinsip yang Dijaga Ketat

1. **PERSISTENSI** — Antran di IndexedDB, tidak pernah dihapus saat app ditutup/restart.
2. **KONFIRMASI SERVER** — SATU-SATUNYA alasan item keluar adalah HTTP 200/201 dari server.
3. **ANTI-STUCK** — Watchdog timer + exponential backoff + kunci proses.
4. **IDEMPOTENSI** — Trip dengan ID sama tidak duplikat di antran.
5. **AUTO-RETRY** — Koneksi pulih → probeServer() → proses antran.

### Alur Proses Sync yang Benar

```
1. App init → processQueue({ force: true, retryAll: true })
2. Event 'online' → probeServer() → processQueue({ force: true, retryAll: true })
3. Polling interval → probeServer() → processQueue()
4. Manual sync → probeServer() → processQueue({ force: true })
```
